## 1 外部项目如何使用

### CAPIE 和 Script SDK

CAPIE 的公共文本框协议可以把玩家填写的文本交给 Mod 的脚本效果。它解决的是输入桥接，执行能力仍受 HOI4 脚本效果本身限制。它没有直接提供完整的科研、生产线、师移动和前线命令 API。[脚本协议](https://github.com/capie-mods/capie/blob/0350d1f6cd662d75936f8cce43afedbcc6b81544/plugin/capie/CONTRACT.md)

固定版本上游未发布公共下载，安装器有预发布限制；本项目现已源码构建并在本机 1.19.4.2 验证双字段输入、脚本回执和存档变量，见 [CAPIE 实验](experiments/CAPIE_20261108.md)。CAPIE 另有开发构建的 `capie_cmd`，底层转交游戏自己的 `eval_effect`；控制台在联机和铁人模式不可用。[项目状态](https://github.com/capie-mods/capie/blob/0350d1f6cd662d75936f8cce43afedbcc6b81544/README.md)、[控制台协议](https://github.com/capie-mods/capie/blob/0350d1f6cd662d75936f8cce43afedbcc6b81544/plugin/capie/CONTRACT-console.md)

本机 `hoi4.exe` 的 SHA-256 为 `BCCC62909B6A1EC2C1D5A46EF18608E4D0C7CDC89AD341B7402A23C40F7A8037`，与 CAPIE 1.6.1 移植目标完全相同。可以直接安排源码构建和 API level 2 的小型实验，无须等待另一次版本移植；哈希匹配只证明构建目标相符。[移植记录](https://github.com/capie-mods/capie/blob/0350d1f6cd662d75936f8cce43afedbcc6b81544/docs/research/port-1.19.4.2.md)

**接入方式**：做一个 IRON 输入面板，先传入序号和一个短参数，Apply 后由脚本输出带序号的日志回执。通过后用于参数化查询和确有对应脚本能力的命令。第一版只传简短字段，不把完整 JSON 塞进文本框。开发构建的 `capie_cmd` 作为第二个实验，失败不阻塞主路线。源码构建放在独立依赖目录；发布分发前核实上游实际许可证，目前仓库称 MIT planned。

### HOI4-AI

该项目的模型路线是截图到视觉策略、记忆网络和鼠标键盘动作，已有行为克隆和强化学习基础设施；仓库仍将其列为研究原型，不能当作可直接参赛的成熟 Agent。[项目说明](https://github.com/noahsabaj/HOI4-AI/blob/73595d38c132d1c2bb10269effe09beb187972a7/README.md)

**复用两部分**：

- Rust desktop worker：截图、鼠标键盘、失焦释放、看门狗和 F12 急停。通过独立进程的 JSON 协议调用，固定上游版本，不引入训练和模型权重依赖。Windows worker 的构建依赖没有 PyTorch 或 CUDA。[构建文件](https://github.com/noahsabaj/HOI4-AI/blob/73595d38c132d1c2bb10269effe09beb187972a7/crates/desktop-worker/Cargo.toml)
- 竞技场生成与比赛记录设计：以后需要短时、对称战斗场景时再复用。先在现有地图验证控制链，避免开局同时承担地图调试。

worker 的上游 match 模式禁止控制台、暂停和调速，与 IRON 的回合制调度不同。若接入，由裁判在受控 setup 阶段完成管理操作，再切回普通输入；不把上游对战模式当成可直接替换的完整后端。[Python 客户端](https://github.com/noahsabaj/HOI4-AI/blob/73595d38c132d1c2bb10269effe09beb187972a7/src/hoi4_arena/desktop.py)

### Agentic HOI4 Modding 和 HOI4 Live Tools

Agentic HOI4 Modding 目前已经包含运行中游戏的测试路线，其中 Windows 的 **HOI4 Live Tools** 比单纯的 Mod 开发索引更接近本项目需要。[接入说明](https://github.com/klimPaskov/Agentic-HOI4-Modding/blob/daf409fcba6c3f7c4bf68109d453f02874a71892/.claude/skills/hoi4-live-playtest/references/setup.md)

HOI4 Live Tools 的 Windows Python 版提供状态、截图、控制台、效果脚本、存读档、日志、时间推进，以及科研、国策、生产和军队等界面操作。当前说明称 Windows 的基础操作在 1.19.4.1 实测，完整战役尚未验收；原生 Windows 内存适配器未完成。中文界面、当前 1.19.4.2 和跨国家操作必须另做本机验证。[当前上游说明](https://github.com/klimPaskov/HOI4-Live-Tools/blob/f644f9a0c8f86c8d8d635687b93116437870e085/README.md)

**采用顺序**：优先验收 Windows Python 版已有操作，合格部分作为 IRON 的执行后端。失败部分用 HOI4-AI worker 配合本项目的中文界面操作补足。只保留一个实际接管桌面的后端，避免两个组件争抢输入。

上游当前 README 与套件内 provider 文档在默认模式、模式切换等细节上有差异。实施时固定版本，读取实际工具定义与源码后封装。需要控制台时由裁判使用 test 能力，Agent 只能提交正常玩法动作。上游 launcher 要求 Steam 等进程退出，因此先验证连接已有游戏；需要它管理启动时，再单独处理其启动条件。

## 2 第一版比赛如何运行

所有 Agent 控制同一个单人游戏进程中的不同国家。游戏暂停时，从同一时刻的状态生成各国观察；各模型可以同时思考，随后由裁判依次下令，全部处理完才推进共同时间。

```text
                         Python 裁判与调度器
                      暂停 / 快照 / 时钟 / 结果
                                |
                 同时刻生成彼此隔离的国家观察
                       /                    \
                 Agent 1                  Agent N（N=3–5）
                 国家 1                   国家 N
                       \                    /
                        结构化动作与简短理由
                                |
                 参数与规则检查 → 串行执行 → 验证
                                |
                  全部执行结束 → 共同推进 → 再暂停
                                |
                 文本存档 + IRON Mod 日志 + 截图
```

各国共享公开外交消息；定向私信只交给发送者和接收者。本国详细状态、私密计划和裁判反馈分别隔离。两轮公开沟通后可发送一次定向私信，再同时提交密封决定，裁判审查后串行执行。切换国家和调速属于裁判管理操作，不计入 Agent 的玩法动作。

### 必须最早验证的条件

1. 暂停期间切换 配置中的全部国家，不让时间偷偷前进。
2. 各受控国家离开玩家视角后，其原生国家 AI 不重排生产、科研、军队和外交。按国家切换 AI 的控制台能力先查本机帮助再实测；切换式命令不能在恢复时盲目重复。
3. AI 关闭后，已有师移动、战斗和战斗计划执行是否仍符合所选玩法。原生国家战略 AI 与战斗计划自动执行分别验收。
4. 切换回来后，先前下达的指令仍保留；读档后控制状态也能重新核实。
5. 推进一天后，各方观察来自同一个完成时刻。

**五项通过后，才采用单进程多国模式。** 如果无法可靠抑制接管，转向独立客户端联机，每个客户端长期拥有一个国家。联机版本改用玩家界面或已验收的同步命令路径，停用单人控制台桥；先用两台 Windows 主机或独立桌面会话验证，同机双实例只列为资源实验。CAPIE 的联机文本框路线要另做双端一致性验收。

## 3 观察和动作的最小合同

### 国家观察

每次观察包含 `match_id`、`turn_id`、`country`、游戏日期、状态来源和采集时间。先覆盖能支撑本阶段动作的数据，再逐步增加：

| 数据域 | 需要的数据 | 主要来源 |
| --- | --- | --- |
| 政治与国策 | 政治点数、稳定度、战争支持度、当前国策与进度、可用选择 | 文本存档；可用性由界面或验收过的查询补充 |
| 科研与工业 | 正在研究、空槽、生产线、分配工厂、建造队列、装备库存和缺口 | 存档的明确字段路径 + 界面核验 |
| 陆军 | 师 ID、位置、组织度、兵力、编组、当前指令、前线情况 | 已验证的存档字段；缺失的实时数据用界面／专用探针 |
| 战争与地图 | 交战各方、控制权、邻接、地形、补给与投降状态 | 存档、原版静态文件、日志与必要的界面读取 |

保留 `tools/parse_save.py`，逐项把递归寻找首个同名键改成经真实存档校准的字段映射。例如国家可用人力不能混入部队编制字段，按 owner 加总工厂也不能直接叫“当前可用工厂”。未知值标为空并注明原因。

大存档优先用于回合快照与恢复；轻量日志用于日期、关键事件和动作回执。实际回合耗时必须统计保存和读取两部分，同时记录五国规模下的总开销。

第一版联调使用明确标注的“各方公开状态”模式；同一份过滤后的公开快照提供给各方。之后增加“各国视角”模式：本国详细状态、公开外交与地图、已验证可见的敌情，敌方隐藏生产和计划不进入模型。两种模式分开记录成绩。

### 动作合同

模型提交的是 IRON 内部动作，而非游戏脚本或任意控制台命令。以下字段是拟定的内部接口：

```json
{
  "turn_id": 12,
  "country": "GER",
  "actions": [
    {
      "id": "12-GER-1",
      "type": "research.start",
      "args": {"slot": 1, "technology_id": "从候选表选择的真实ID"}
    }
  ],
  "reason": "补齐当前工业研究空槽"
}
```

调度器在上下文中提供本轮合法候选和可调用动作。初期支持：国策选择、科研开始、建造排队、生产线与工厂分配；随后增加军队编组、移动、前线、攻势启停和事件选项。外交、空海军和情报在陆战闭环之后接入。

每个动作记录 `applied`、`rejected` 或 `unknown`，附验证依据。以科研为例，成功要看到目标科技进入指定槽，不能只以键盘输入已发送为准。结果不明时先重读状态再决定是否重试，避免重复建造和重复点选。

执行优先使用已经验收的正常玩家操作。脚本效果用于读取、回执、比赛设置和确有正常命令等价性的动作；不能用“直接完成科技／国策”“瞬间造工厂”等效果代替正常选择和排队。效果本身可能绕过规则，必须核验资源消耗、前置条件和时间消耗。

## 4 回合与模型调度

回合状态依次为：暂停确认 → 同时刻采集 → 公开讨论 → 定向私信 → 私密决策 → 裁判审查 → 串行执行与验证 → 共同推进 → 暂停确认。

- 经营联调采用每回合 15 游戏日，每 24 小时暂停核验时钟。陆战需要时缩短执行检查窗口，战略决策仍由比赛规则统一规定。对所有参赛方使用相同时间窗口。
- 以实际游戏日期和暂停状态判断推进完成，墙钟只做超时限制。先低速验收，记录实际推进终点和偏差；严格定时暂停若做不到，不宣称精确到小时。
- 先完成所有 Agent 决策再执行，避免后决策者看到先行操作。执行顺序每轮轮换；战争中外交与即时冲突动作另定顺序规则。
- 当前模型请求失败即停止该决策阶段；只有五份原请求都获批准才执行。后续比赛规则可规定超时保持已有指令。输入或状态验证失败时停在暂停态处理，不继续盲走。
- 科研完成、国策完成、事件弹窗和战争变化可触发提前决策。阻塞事件优先交给对应国家 Agent；各方都不能从另一方的私有弹窗得到信息。
- 每国单个 Agent，通过可替换模型客户端接入不同供应商。当前保留最近两回合本国历史，每国每轮最多一个已校准动作；长期计划与更多动作待后续扩展。模型名、参数、完整提示词、调用量和耗时随对局保存。

自动暂停与焦点操作只在执行进程可确认时进行。失焦时先释放输入，再报告状态；不要把 worker 的“释放按键”误写成“游戏一定已暂停”。最近完成的回合快照作为恢复起点。

## 5 分阶段实施与验收

### M0 验证后端与多国控制

产物：环境记录、控制通道实验报告、选定的执行后端。

1. 记录游戏版本、完整 exe 哈希、Mod 列表、语言、分辨率、UI 比例和初始存档。当前保存的快照为 1.19.4.2，新对局以实测为准。
2. 试用 HOI4 Live Tools 的状态、截图、单条控制台、一次正常科研操作和推进一天。安装用独立环境，先不自动注册到全局客户端配置。中文界面和现有启动方式通不过的部分，记入缺失能力。
3. 需要补足截图或输入时，独立构建 HOI4-AI 的 Rust worker，验证失焦释放、恢复与急停；采用本项目的后端诊断入口。
4. 在备份测试局中验证第 2 节的五个控制条件，至少交替控制五国连续推进 10 天。
5. 独立做 CAPIE API level 2 的最小输入—日志回执实验。成功后再决定是否维护该适配器。

**通过条件**：确定一个可用后端；五国控制状态不会被原生国家 AI 偷换，各方能在共同日期持续下令。若单进程失败，报告具体失败点并实施独立客户端验证，后续 Agent 接口沿用。

### M1 修复和稳定感知层

产物：仓库内可部署的 IRON Probe Mod、国家观察 JSON、字段校准记录。

新的 Probe Mod 由项目源码部署：采用正确的 `on_actions` 外层，仅采集配置中的 3–5 个国家，按实际回调作用域避免重复遍历。探针启用与实际日志输出一并验收。

采用每国每日一条必要摘要，并增加显式探活与动作回执。已有存档加载不能单靠 `on_startup` 判断 Mod 正常；暂停时的即时观察通过显式查询或存档取得。政治点数等变量表达式要与 UI 对照，确认没有将未定义变量的零值当成真实状态。

**通过条件**：五国连续 10 日的日期和摘要无重复、无串国；本国关键字段与同一暂停时刻的 UI 对照；日志轮转或重启后不读取旧回执。现有解析器自测继续通过，新增测试针对真实字段路径和同名键混淆。

### M2 建立正常玩法动作

产物：动作定义、执行器、结果验证器及单国脚本化回合示例。

先用确定性的测试策略执行：开始一项科研、选择一个合法国策、增加一个建造队列项、调整一条生产线。每个动作都验证国家、目标、队列变化与正常消耗。补齐事件弹窗处理。

**通过条件**：单国连续 10 个回合完成观察—操作—验证—推进；非法选择被拒绝；故意中断一个动作后恢复不会重复操作。通过后用同一执行器轮流控制 3–5 个国家。

### M3 接入 3–5 个独立 LLM Agent

产物：模型客户端、国家上下文、多 Agent 回合调度、逐轮记录。

先用三国配置做 30 游戏日经营联调，再以 GER、ITA、JAP、ENG、SOV 五国配置重复验收。五国暂不承担正式比赛胜负，重点检查计划延续、候选动作理解、跨国隔离和原生 AI 接管。每个 Agent 仅通过动作接口改变游戏。

**通过条件**：3–5 个 Agent 持续提交并执行正常决策；能追踪未执行／失败的动作；运行记录能区分模型决策错误、执行失败和观察错误。保留每轮实际游戏时间、总耗时、token 用量和动作成功率。

### M4 实现第一场陆战对局

产物：固定起始存档、陆军动作与地图定位、终局检测和可回看对局。

先在原版地图准备一个至少三国参与、已有部队且已开战的测试局，再扩展到五国。设置仅在比赛开始前进行并写入记录。增加编组、普通移动／攻击、前线与攻势启停；默认复用玩家可用的战斗计划执行，并明确其参与范围。

对地图操作读取本机省份 ID 与静态邻接，建立 ID 到屏幕目标的定位；通过当前位置或当前指令验证选中了正确部队。缺少可靠位置／组织度时补专用观察，不让模型靠国力摘要猜战场。

之后按需接入 HOI4-AI 的对称小地图，验证该版本地图能加载、开战、补给、投降和结束，再作为正式短赛场景。

**通过条件**：3–5 个 Agent 都能对自己的部队下令；实际发生战斗；以预设结束日或剩余阵营条件结束完整比赛；单国投降只淘汰该国，不自动结束全局。Mod 的投降日志与存档／界面互相核验，同盟胜利与个人排名分开记录。完成国家轮换的多场对局。

### M5 扩展到完整国家经营与多方比赛

逐项接入外交、贸易、空海军、情报和和平会议；每项沿用同样的观察—动作—验证合同。保持 3–5 国规模，支持联盟、对其他 Agent 的外交和更长的原版战役。

正式模型比较固定游戏版本、DLC、规则、起始存档、观察模式、提示词和模型预算。不同模型交换国家，并进行多局重复；游戏随机种子和所有模型参数留档，设置 seed 不作为跨机器完全确定性的保证。

**完成标准**：持续运行至比赛终点，故障与胜负能区分，记录足以定位每项重要决策和实际结果。分别报告胜负、投降时间、无效对局、动作执行成功率、模型成本和墙钟时间，避免将执行故障计作策略能力。

## 6 代码与产物组织

在当前工具上逐步增加，某一阶段不需要的模块暂不创建：

```text
IRON/
  README.md
  docs/
    TECHNICAL_ROADMAP.md
    experiments/                 后端与游戏内验收记录
  tools/
    parse_save.py                复用并校准
    live.py / live_compat.py     后端入口与本机适配
  mod/ironprobe_mod/             探针源文件，部署到游戏用户目录
  src/iron/
    observe.py                  观察、来源与可见信息过滤
    game.py                     所选执行后端、暂停与游戏时钟
    actions.py                  动作合同、执行与结果验证
    agent.py                    模型客户端与国家计划
    match.py                    国家切换、回合调度与终局
  configs/
    local.example.json          路径、后端与参赛配置
  playbook/                     国家与战场攻略
  runs/<match_id>/
    manifest.json               环境、规则、模型、初始存档校验值
    turns.jsonl                 各轮观察摘要、动作、结果与理由
    checkpoints/                完成回合的恢复存档
    evidence/                   关键截图与日志片段
```

密钥走环境变量，不写入配置或比赛记录。初期以 CLI 为入口，先提供环境检查、单轮运行、指定回合数比赛和恢复运行；Web 面板在对局跑通后再做。

## 7 从现在开始的执行顺序

先实施 M0 的现成 Windows 工具验收和五国控制实验，确认多 Agent 能共同控制一个世界。随后稳定 M1 的观察和 M2 的正常玩法动作，再投入 LLM 与攻略设计。

CAPIE 在 M0 内安排一个独立小实验：输入序号 → Mod 接收 → 日志回执。通过则加入可用后端；未通过则保留证据，主线继续使用已经验证的控制通道。

本路线的第一个可演示结果是“五国共用时钟、连续下令 10 天”；第一个 Agent 结果是“3–5 模型经营 30 天”；第一个竞技结果是“3–5 模型完成一场陆战”。三者分开验收。
