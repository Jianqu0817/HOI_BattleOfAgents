## 一、技术链现状(审阅结论)

### 1.1 分层结构

整条链是:**游戏进程 ← 原生 DLL ← 命名管道 RPC ← Python 调度器 ← LLM API**,顶部产出可回看的对战视频素材。

| 层 | 内容 | 关键事实 |
| --- | --- | --- |
| L1 游戏执行层 | `native/iron_bridge` C++ x64 DLL | MinHook detour `hoi4.exe` 窗口 tick 线程(RVA `0xBDB570`);调用游戏普通命令队列,不开控制台、不发键鼠输入;硬编码 exe SHA-256 + 26 字节序言签名双重校验(`bridge.cpp:28-29`);`IronRegisterOperation` ABI 允许扩展模块(clock/control/move/diplomacy/air_navy)不替换已加载 DLL |
| L2 执行可靠性 | `native_game.py` / `native_rpc.py` | WAL 式意图日志(先落盘 intent 再派发)、request_id 幂等重放、进程创建时间防 PID 重用、期望值前置校验、回执≠生效(applied/rejected/unknown 三态)、永不自动重试游戏变更 |
| L3 观察层 | `parse_save.py`、`native_observation.py`、探针 Mod | 存档解析器 + 原生观察采集 + scripted_gui 日志回执;各国观察隔离靠调度器约定,非游戏级迷雾 |
| L4 决策层 | `model_client.py`、`showrunner.py`、`lessons.py` | 零依赖 urllib OpenAI 兼容客户端;生成参数严格白名单;密钥只走环境变量;分层 prompt(共同规则/游戏说明/人设/本国经验);每国、裁判、解说各用各的模型;经验记忆带适用条件与置信度,不改权重 |
| L5 裁判调度层 | `campaign.py`、`scoreboard.py`、`verify_campaign.py` | 文件锁、分阶段恢复、执行顺序轮换、独立裁判审查、三种计分、1,158 项记录审计 |
| L6 内容生产层 | `episode.py` | HTML 回看、观众解说、SRT、CSV/JSONL、镜头表、截图素材、UTC 场记 |
| L7 工程质量层 | unittest + GitHub Actions + `.deps/` | 116 项离线测试(合成宿主,不碰真游戏);Win+Ubuntu CI;第三方依赖源码固定(MinHook 按 revision checkout) |

### 1.2 演进脉络

UI 自动化后端(HOI4 Live Tools)→ CAPIE 文本框桥(实验)→ 原生 DLL 注入(现主线)。`campaign.py` 执行器仍走 UI 通道,原生军事入口单独运行、逐项迁移而非一次切换。

### 1.3 值得肯定的设计

RPC 幂等设计、PID 重用防护、期望值前置校验、意图先落盘、`PIPE_REJECT_REMOTE_CLIENTS`、`FILE_FLAG_FIRST_PIPE_INSTANCE`、全链 fail-closed。真正的短板不在"已想到的地方",而在下文"没想到的地方"。

## 二、问题与风险清单(按严重程度)

### 2.1 最大的问题:维护悬崖(项目级风险)

整条"验证执行"命脉悬在一个单人逆向维护点上:

1. Paradox 每发一个补丁,原生链死一次——不是重编译,而是重新逆向定位 RVA、重验签名。五个原生模块全部建立在同一假设上。
2. 当前兼容是"捡来的":本机哈希恰与 CAPIE 1.6.1 移植目标相同,RVA 和签名实质来自上游逆向成果。下次更新若上游不同步移植,负担完全自担。
3. 项目的核心价值主张("每个动作有证据")全部押在这上面;UI 降级后端还须同时维护,这正是 roadmap 自己警告的"两个组件争抢输入"的根源。

**对策方向**:把 RVA/签名/哈希提取为带验收流程的版本清单(数据文件而非代码常量);为"新补丁如何定位新 tick"写一份可重复的逆向 procedure。

### 2.2 中等严重度

- **跨 Agent 提示注入(设计内生)**:"允许合作、隐瞒和欺骗"意味着他国消息本来就是对抗性内容,防线只有 `showrunner.py:152-155` 一句系统提示(提示级隔离,非结构级)。裁判与解说模型同样读全部消息,可被"带节奏"。缓解因素实打实:`action_options` 白名单、裁判审查、执行校验、承诺逐字核对兜底,注入最多把模型骗出**糟糕的游戏决策**,骗不出**非法操作**。未覆盖的是认知层面:"被对手操纵"与"策略失误"在记录中无法区分。
- **观察层根信任未建立**:`parse_save.py:370` 递归找首个同名键,同名键混淆会把错误语义混进观察(roadmap:104 自认)。链路是:错误观察 → 错误决策 → "执行成功但策略错误"。三态验证保证不了意图建立在真数据上。

### 2.3 低严重度(安全类)

- **管道默认 ACL 含 Everyone 读**:`bridge.cpp:167` `CreateNamedPipeW` 末参传 `nullptr`,按 MSDN 文档默认描述符给 Everyone/匿名账户读权限,同机其他低权限会话可读回执。单机单人场景危害小,几行 SDDL 可关。
- **注入 DLL 的检出与合规**:MinHook 注入是杀软启发式经典特征,已有 ADR 要求发布前 AV 扫描;Steam 单人无反作弊,封号风险低,EULA 层面灰色。作为内容创作项目可接受,作为分发产品是死结。

### 2.4 低严重度(工程类)

- **回执缓存无界增长**:`bridge.cpp:149` 每个请求 ID 永久存入 `receipts`,长对局缓慢泄漏。
- **journal 并发竞态**:`native_game.py:38` 两个进程同时提交同一新 request_id,`open("x")` 败方拿到未处理的 `FileExistsError` 直接崩。campaign 锁实际会串行化,触发条件苛刻,但防御不完整。
- **桥卡死无自愈**:操作在 tick 线程执行,某操作挂住主线程则 worker 无超时等待,管道永久停服;唯一恢复路径是重启游戏,一整回合报废。与"永不自动重试"一致,但代价要知晓。

### 2.5 低严重度(运营类)

- **`runs/` 回看 HTML 含全部秘密**(私密意图、私信、裁判反馈):若整个 runs 目录被当作作品发布,秘密全泄。需要"公开发布只走导出管线,绝不开 runs 目录"的操作纪律,或做发布视图过滤。

## 三、产品设计需求评审(七项提问的结论)

### 3.1 Agent 之间对决策与发言的互动(互损/支持/吐槽)

**核心矛盾:决策密封,Agent 只能对"后果"互动,不能对"决策"互动。** 两步方案:

1. **上一回合决定的"事后公开摘录"注入下一回合公开讨论**——执行结束后决定已不是秘密(观察里都有),事后公开不违反密封原则(密封只防事前反应)。给模型选择权:动作加可选 `public_reason` 字段,`reason` 仍密封。"表面说辞与实际相反、观众全知、玩家不全知"本身就是节目张力。
2. **公开消息 schema 加 `asides[]` 结构化吐槽通道**,不加新阶段:

```json
{"country": "GER", "message": "...", "commitments": [...],
 "asides": [{"about": "ITA", "stance": "mock", "ref": "12-public-3", "text": "……"}]}
```

- `ref` 必须解析到公开账本真实 ID(复用"承诺逐字核对"验证哲学,防编造)
- `stance` 枚举(mock/support/taunt/gloat/lament/neutral)支撑"互损排行榜"等节目化统计
- 挂在现有 diplomacy 调用输出上,零额外调用

### 3.2 裁判对参赛 Agent 的吐槽互动

**原则:执法与综艺解耦,但可同源。** 裁判 verdict 输出加可选 `host_note`(≤80字,观众向),验证器强制只引用已公开事实,引用密封信息即过滤。verdict schema 不动,validator 保证吐槽污染不了执法;prompt 明确 host_note 不影响判定。host_note 是观众内容,**不回流玩家 prompt**。裁判做"场内角色"(可申诉/贿赂)留作后续赛季特性,第一季保持幕后。质量不够再拆独立主持人模型。

### 3.3 回合天数、精细操作与垃圾时间

**当前设计(快配置 24h、经营 360h)对 v1 合理,对战争不合理。** 问题不是天数选错,是粒度固定:和平期 24h 步进浪费调用,战争期 15 天步进让军队 AI 半自主、精细指挥失效。

**推荐:回合(决策周期)不变,时钟推进改条件式**——给 clock sidecar 加"step until {目标日期} OR {出现待处理事件} OR {战争状态变化}":

- 和平期一次推 15-30 天;有战争自动降 24h(战争状态已有追踪);决战日特殊场景可降到 12h
- 精细操作下限取 24h(HOI4 师移动本身要几天,小时级步进只增加调用不增加指挥质量);真正瓶颈是 `action_limit=1`,战争回合需放开到 3-5 个动作,与战争切档一起设计
- 垃圾时间分两层:游戏层条件推进(省录制墙钟与 OBS 存储,大头)+ 视频层导演剪辑(省观众时间)
- 替代方案排序:事件驱动变长回合(推荐)> 固定长短混合 > 实时推进+检查点(存储膨胀、同刻观察不变量变脆)> 各国独立时钟(破坏共同时间根基,否决)

### 3.4 弹窗处理

**目前完全未实现(clock.cpp 与 native_game.py 均无 event/popup 逻辑,roadmap 仅计划)。** 核心原则:**不依赖 UI**:

1. 游戏设置关掉绝大多数自动暂停弹窗,源头减少
2. bridge 加 `native_events` 操作,内存枚举待处理事件,**按国家划分可见性**(GER 的国策完成事件是 GER 私有观察;宣战是公开信息)
3. 事件内容(标题/描述/选项,静态文件+存档)进对应 Agent 的结构化观察
4. 加"用选项 X 回答事件"原生操作,调 UI 按钮同一函数,与 `native_move post` 哲学一致
5. 回答前截图 → 事件变 episode"事件卡"素材,后期覆盖层渲染,**正片不需要弹窗出现在画面上**;实机录制从检测到回答几百毫秒
6. 兜底:已知清单外的未知模态弹窗 → 停在暂停态、journal 保留 request_id、人工对账;绝不盲点
7. 与 3.3 的条件推进共用检测机制,两者是一件事的两半

### 3.5 设定卡、立绘、TTS 的预留

**原则:只定数据落点不实现合成;文本正典,立绘音频派生。** 三处预留:

- **配置层**(每国):

```json
{"character_card": {"display_name": "...", "title": "...", "color": "#...", "tagline": "...", "traits": []},
 "portrait": "assets/portraits/ger.png",
 "voice": {"provider_env": "TTS_API_KEY", "voice_id": "...", "style": "...", "speed": 1.0}}
```

- **episode 层**:HTML 每条发言加 `data-country` + 头像占位(`data-portrait-src`);episode 开头加 `kind: "card"` 亮相事件;字幕旁输出 `voice_lines.jsonl`(line_id/text/country/style/visibility)供批量 TTS;SRT 不变,剪辑对齐工作流不受影响
- **存储层**:`runs/<match>/assets/`(gitignored);TTS 在解说定稿后离线跑,供应商抽象、密钥走环境变量,与 model_client 同风格

### 3.6 导演 Agent 总结枯燥内容并加速

**导演必须是 runs 数据的离线消费者,绝不进游戏主循环**——后期制作、玩家不可见、全知无泄密,是全项目最安全的放模型处。输入 episode JSON,输出 EDL 剪辑脚本:

```json
[{"kind": "fast", "from": "t=360", "to": "t=840", "speed": 8},
 {"kind": "summarize", "from": "t=840", "to": "t=1200", "narration": "……", "voice": "referee"},
 {"kind": "freeze", "at": "t=1210", "note": "宣战时刻"}]
```

验证器:所有时间戳解析到 episode 事件、每国每集至少出场一次(戏份平衡)、narration 长度上限。**先做规则版兜底**(连续 N 小时无事件 → 自动 speed 8 草稿),LLM 导演只写旁白与选高光。导演与解说是两个 persona 两个配置,不合并。

### 3.7 逆向可靠性

**结论:锁定 1.19.4.2 上可靠;跨版本每次都是硬仗。** 全链 fail-closed:哈希不符拒载(return 11)、序言签名不符(12)、MinHook 失败(13)、已有 detour 拒载、合成宿主拒收游戏操作、未知操作拒绝、超时一律 `unknown` 不标成功。**"无法操作"会以响亮错误呈现,不会静默出错**——比 UI 自动化链路本质上更可靠。

生产中"无法操作"按概率排序:① 未知模态弹窗卡住推进(3.4 方案,唯一完全未实现的场景);② 推进中崩溃(journal 幂等对账已覆盖);③ 其他 Mod 注入同一 tick(响亮拒绝)。

**仅剩的静默风险**:观察侧内存读取偏移量给 plausible garbage——命令侧有"回执≠生效"防护,读取侧没有等价物。对策:每回合抽 2-3 个字段(如某师位置、某国人力)同时走原生读取与存档解析,漂移超阈值告警。这一条做不做,决定"观察可信"是宣称还是证据。

## 四、审阅中发现的同类问题(五项观察)

1. **承诺永远不会被裁决**:`remember_commitments`(`campaign.py:224-237`)只做合并和截 100 条上限,`status` 永远 "unverified"——"状态未核实"永久为真,到期承诺无任何机制判"兑现/背弃/无法核实"。对策:裁判每回合扫到期承诺、对照公开事实出裁决 → **承诺兑现榜**。既是公平机制也是最好节目素材;社会压力会让 Agent 认真对待承诺,机制本身改变模型行为。
2. **公开通道体积**:5 国 × 两轮 × 300-400字/轮全部进每个 Agent 后续 prompt;加吐槽通道后膨胀更快。对策:逐字保留最近一回合,更早卷成裁判摘要。本国历史已限两回合(`campaign.py:211` 取 `records[-4:]`),公开账本无等价压缩。
3. **经验记忆自我偏见**:lessons 来自本国证据,自我服务结论带置信度持续累积。对策:裁判每回合对新 lessons 做矛盾扫描,或过期重验。
4. **裁判模型厂商偏置**:裁判与某参赛国同厂商同源时,审查中立存疑。manifest 已记录模型厂商,补"裁判模型轮换或至少声明"规则。
5. **录制环境卫生**:Windows 通知、Game Bar、输入法悬浮窗进 OBS 画面。`doctor` 加"录制环境检查"(免打扰预设、通知关闭)是半小时的活,省整段作废素材。

另:决策错误与"被对手操纵"在 M3 验收口径中无法区分,建议记录里加"对方消息含指令样文本"标记字段。

**实施批次:**

1. **批次一(引擎保命)**:序 3 + 4 + 补充项 E 一起做——三件事共享"条件推进 + 事件检测"一套机制;附带序 7 的观察对账。

## 七、结论

- **最大的问题不是某行代码,而是项目最核心的资产——可信执行链——建立在一个随时会失效且需要逆向技能才能修复的假设上**(哈希+RVA 焊死在 `bridge.cpp:28-29`)。
- **最现实的漏洞是对抗性 Agent 格式内生的提示注入**,目前只有提示词级防线;结构级兜底(白名单、裁判、校验)已经把伤害限在"错误决策"内,但"被操纵"与"失误"尚未区分。
- **七项设计需求里,3+4(条件推进与弹窗)是保命项且必须合着做,1+2+8 是灵魂项且便宜得惊人;新增需求里 B(预测结算)和 A(赛季回顾)几乎是白捡的节目效果。**
- 设定卡、TTS、导演等新功能全部可以做成 runs 数据的离线消费者——"runs/ 全量 JSONL + 离线测试 + 模型调用留痕"的纪律恰好是它们的最好地基,不需要动任何现有架构。这是新需求面前罕见的幸运,不要破坏它。
